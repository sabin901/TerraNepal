# Production and free-resource review — 4 November 2026

## Decision

Keep GitHub Pages and Actions for the current noncommercial research dashboard.
The tested pipeline can collect, preserve selected revisions and publish without
the owner's computer. It is not yet a validated flood forecasting or warning
service. Improving geographic matching and evaluation is more valuable now than
adding more API feeds or replacing the hosting stack.

## Material finding and correction

The selected Karnali study coordinate returned a model daily mean of **0.81 m³/s**
for 4 November. A neighboring returned grid cell approximately 0.05 degrees west
returned **1,134.01 m³/s** for that same model date. Nine nearby coordinates were
queried in one documented multi-location API request. The two returned cells were
`28.675003, 81.275024` and `28.675003, 81.225006`.

This is evidence of spatial sensitivity, **not evidence that the larger value is
the correct gauge forecast**. Picking the maximum nearby discharge would not
establish river identity. Open-Meteo explicitly cautions that its grid can select
the wrong river. The raw source response and request metadata are retained in
the local review report; no source values were rewritten.

The public table now requires `reach_verified === true` before displaying any
numeric discharge outlook, in addition to the retrieval-age rule. All six
current points remain unverified and their numeric outlooks are withheld. The
original model outputs remain in the clearly marked research JSON/history.
Regression checks cover missing, false and non-boolean verification flags,
stale/future retrievals, and actual browser table cells.

A second recovery defect was found in history persistence. A catch-up was
written as one compressed file, but publication rejects files expanding beyond
32 MiB. The first retained batch averaged approximately 549 bytes per selected
observation version, so a multi-day recovery could exceed that cap. Large runs
are now split into immutable parts of at most 16 MiB uncompressed, retaining all
versions while advancing the run counter only once. The storage/verifier limits
remain in place; this does not increase the total history budget.
A synthetic 80,000-record recovery preserved all 80,000 records across three
parts, each accepted by the publication verifier. Synthetic records were kept
in a temporary test directory and were never published as observations.

## What is working, and its limits

- Both latest application deployments and their backend verification workflows
  succeeded when checked. The latest reviewed public snapshot was built at
  **06:24:51 UTC** (00:24:51 America/Chicago) on 4 November.
- Three public collection snapshots were retained. Git restoration recovered
  earlier state and added observations without replacing history. Approximately
  1.2 MB was stored in the data branch's current tree at review time.
- The snapshot reported 171/205 retained river stations and 304/397 rainfall
  stations with observations no more than two hours old at collection time.
  These are freshness counts, not sensor-accuracy or nationwide-coverage scores.
- Incident totals and the historical gap audit remain separately dated local
  exports. They are not automatically updated by this cloud workflow.
- No independent monitor currently checks publication age when GitHub's own
  scheduler stops. A successful HTTP response alone cannot detect stale data.
- Source response checksums in cloud history are not full raw-response backups.
  The local raw archive and its backups remain necessary.
- The 256 MiB current-tree cap protects repository size but will eventually
  require an explicit storage decision. Three closely spaced runs are not enough
  to estimate a credible retention lifetime.

## Improvements in priority order

| Priority | Improvement | Acceptance evidence |
| --- | --- | --- |
| 1 | Confirm each model reach and each gauge's identity, units and datum | Documented river-network/drainage-area match and independent gauge metadata; coordinate proximity alone is insufficient |
| 2 | Evaluate forecasts against later observations across wet seasons and severe events | Per-basin lead-time metrics, missing-data accounting, comparison with persistence, false alarms and missed events; no future-data leakage |
| 3 | Add catchment precipitation estimates, rather than treating city forecasts as basin rainfall | Explicit watershed polygons, spatial weighting, product version/scaling and comparisons with gauges |
| 4 | Automate reviewed incident aggregates and monitor published-data age independently | Freshness measured separately for each product; outage/recovery exercises that detect a stopped scheduler |
| 5 | Move growing queryable history to appropriate storage when measurements justify it | Measured daily growth, indexed query costs, tested restore and a free-tier budget before migration |

## Alternatives checked

**Google Flood Forecasting** is a useful additional comparator. Nepal is on the
published coverage list. The API is offered at no charge, but requires approval,
a Cloud project, API key and enablement. Coverage of a country does not establish
coverage or skill at every river. It has not been connected or independently
evaluated for this project.

**NASA IMERG** adds satellite precipitation estimates over catchments. NASA
documents approximately four-hour latency for Early Run, so it complements
gauges and is not instantaneous rainfall. The documented PPS download route
requires registration. Rate versus accumulation units and scaling need explicit
handling. No account was created or credentials borrowed.

**Direct official gauge data** could help verify BIPAD station metadata. The DHM
`/hydrology/realtime-stream` endpoint returned a server-error response during
this check. Its data were not ingested, and the error was not treated as evidence
of no river observations. This single failure does not establish that all DHM
services are unavailable.

**Cloudflare D1** is a candidate for queryable history: its current free plan
includes 5 GB total storage, 5 million rows read/day and 100,000 rows written/day,
subject to database and account limits. Index writes also count. A move would
need a new user-owned account connection, schema, batching and quota tests.
Cloudflare Workers Free has only 10 ms CPU per scheduled invocation; it is not a
drop-in home for this Python/SQLite collection pipeline. Keeping Actions for
batch processing remains reasonable. No provider migration was performed.
